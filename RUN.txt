VERSE FINDER — HOW TO RUN IT
============================

Everything below is run from the backend folder unless it says otherwise.

    cd ~/dev/projects/verse-finder/backend
    source .venv/bin/activate

You should see (.venv) in your prompt. Check it worked:

    which python        -> .../verse-finder/backend/.venv/bin/python

If that prints something else, the venv isn't active and nothing below will
work. Just run the "source" line again.


1. RUN THE APP
--------------

    uvicorn app.main:app --reload --port 8000

The backend serves the frontend too (app/main.py mounts frontend/ as static
files), so that's the only process you need. Open http://localhost:8000 in a
browser and type how you feel.

Pick how it searches with the radio buttons under the box:

    One-shot     the original pipeline. One search, ~0.4s.
    Agent        the hand-rolled loop. Searches as many times as it needs, ~15s.
    Agent        the same thing built in LangGraph, ~15s.

Either agent mode adds a "How it searched" panel under the reflection. Click it
open to see every search it ran and what came back. One-shot has no panel —
it made no decisions, so there's nothing to show.

API docs (try the endpoints directly): http://localhost:8000/docs

Startup takes ~20s — that's the mpnet model loading, before the server starts
accepting requests. Once it says "Application startup complete", it's ready.


2. RUN THE TESTS
----------------

    pytest -q                 fast tests. No model, no network. ~0.3s.
    pytest -q -m slow         loads the mpnet model (~20s). Real retrieval.
    pytest -q -m live         makes real API calls. Costs money. Skipped by default.
    pytest -q -m ""           everything.

Run "pytest -q" after any change. It's fast enough that there's no reason not
to.

Useful flags:
    pytest -q tests           only the agent tool tests
    pytest -q evals           only the eval harness tests
    pytest -v                 show each test name
    pytest -x                 stop at the first failure


3. RUN THE EVAL
---------------

This scores a retriever on how much of what a person said it actually answers.

    python evals/run.py --retriever baseline --no-judge
        Retrieval only. No API calls, costs nothing. Just proves the retriever
        returns sane quotes. Writes results/baseline.smoke.json.

    python evals/run.py --retriever baseline
        The real thing. Uses claude-opus-5 to grade coverage.
        Writes results/baseline.json.

Retrievers you can pass to --retriever:

    baseline        one search, top 3. The current app.
    baseline-wide   one search, top 12. The volume control — the agent returns
                    about this many quotes, so this separates "searched better"
                    from "just returned more".
    agentic         the hand-rolled agent loop (stage 2). Slow, ~7-15 min, and
                    it makes real API calls for every query.
    agentic-lc      the same agent built with LangGraph (stage 3). Same model,
                    same prompt, same tool — only the machinery differs.

Verdicts are cached in evals/.cache/, so re-running is nearly free and gives
identical numbers. The first judged run takes about 80s; after that, ~5s.

Other flags:
    --limit 3        only score the first 3 queries (quick check)
    --out FILE       write somewhere else

    --rejudge evals/results/agentic.json
        Re-grade a finished run's stored quotes under the current rubric,
        WITHOUT running the retriever again. Use this after changing the judge:
        re-running the agent would change the quotes too, and then you couldn't
        tell whether a number moved because the judge changed its mind or
        because the agent searched differently.

Where things stand (20 queries, compound-only coverage is the number that
matters — those are the queries the agent exists to fix):

                    baseline  baseline-wide  agentic  agentic-run2  agentic-lc
    facet coverage     0.500       0.717      0.808       0.900        0.883
    compound only      0.412       0.667      0.775       0.882        0.863
    mean top-1 score   0.473       0.473      0.629       0.661        0.627
    API calls / query      0           0       2.70        2.80         2.75
    seconds / query      0.2         0.3         16          16           16

baseline-wide is the control: the same dumb single search, just returning 12
quotes instead of 3. It exists so you can tell "searched better" apart from
"returned more" — more than half the agent's raw gain is volume, and this is
how you see that.

Mean top-1 score is the number to trust most. It's raw cosine similarity with no
LLM judge anywhere in it, and volume can't move it: returning 9 more quotes
never improves the BEST one. baseline and baseline-wide are pinned at exactly
0.473; every agent run lands at 0.63-0.66.

agentic and agentic-run2 are THE SAME CODE RUN TWICE: 0.775 and 0.882. That
0.107 spread is the real noise floor — the agent rewords its searches every run
and retrieves different quotes. agentic-lc (0.863) sits inside that band, so
there's no evidence LangGraph does anything different. Don't read any gap under
about 0.11 as meaning something.

The judge is claude-sonnet-5, not Opus — it's the most-called model here (3x per
facet x 5 retrievers), and grading against a strict rubric doesn't need Opus.
That's checked, not assumed:

    python evals/judge_models.py --offline    opus vs sonnet, costs nothing

It agrees with Opus on 90% of facets, and every disagreement is Sonnet being
STRICTER — never looser. A one-directional bias shifts every retriever the same
way and keeps the ranking, which is all this eval needs.

Other things you can run:

    python evals/judge_stability.py              judge the same quotes 6x
    python evals/judge_stability.py --vote 3     ...the way run.py does

Full write-up of the numbers: backend/evals/results/README.md
How the harness works:        backend/evals/README.md


4. TRY THE TOOL BY HAND              (added in stage 1)
-----------------------------------

    PYTHONPATH=. python -c "
    from app.rag.tools import run_tool
    print(run_tool('search_quotes', {'query': 'anger toward family'})[0])
    "

Compare that against what the plain pipeline returns for a compound query — the
tool finds anger quotes at 0.45-0.49 that the compound query never surfaces.
That gap is the whole reason the agent exists.


5. RUN THE AGENT BY HAND             (added in stage 2)
----------------------------------

This makes real API calls, so it costs money. About 30-60 seconds per run.

    PYTHONPATH=. python -c "
    from dotenv import load_dotenv; load_dotenv('.env')
    from app.rag.agent import reflect
    r = reflect(\"i'm grieving my dad and angry at my family\")
    print(f'searches={r.searches} api_calls={r.api_calls}')
    for s in r.trace:
        print(f\"  {s['step']}. {s['query']}  ({s['returned']} back, top {s['top_score']})\")
    print()
    print(r.reflection)
    "

What you're looking for in the trace: it should search two or more times, with
different wording each time. That is the agent deciding to look again — the one
thing the plain pipeline cannot do.


6. RUN THE LANGGRAPH VERSION         (added in stage 3)
----------------------------------

Same command as above, with one word changed:

    from app.rag.agent_lc import reflect      instead of  app.rag.agent

Same model, same prompt, same tool, same return type. Only the machinery is
different — a while-loop you can read top to bottom, versus a StateGraph.

To SEE the graph run step by step, put these in backend/.env and re-run:

    LANGSMITH_TRACING=true
    LANGSMITH_API_KEY=...        (free account at smith.langchain.com)

Every node, every tool call, every prompt shows up as a visual trace. It is the
best agent-debugging tool you get for two lines of config.


7. HIT THE AGENT OVER HTTP           (added in stage 4)
----------------------------------

The browser is the easy way (section 1). To call it directly, with the server
running:

    curl -s -X POST localhost:8000/api/verses/search/agentic \
      -H 'Content-Type: application/json' \
      -d '{"mainPrompt": "i'"'"'m grieving my dad and angry at my family"}'

Add ?implementation=langgraph to run the other loop:

    curl -s -X POST 'localhost:8000/api/verses/search/agentic?implementation=langgraph' \
      -H 'Content-Type: application/json' -d '{"mainPrompt": "..."}'

The three endpoints:

    POST /api/verses/search            one-shot. Unchanged — this is the
                                       baseline every claim is measured against.
    POST /api/verses/search/agentic    the agent. Same fields plus "trace",
                                       "implementation", "stopped_early".
    POST /api/verses/explain           LIME: which words drove the top match.

"trace" is the list of searches it actually ran, in order — the same thing the
panel in the browser shows. "stopped_early": true means it used up its budget
of 6 turns still searching, and the reflection was written from whatever it had
by then. The quotes are still real; the run was just cut short.

Costs money — every agentic call is 3-4 real API calls.


IF SOMETHING BREAKS
-------------------

"command not found: pytest"
    The venv isn't active. Run: source .venv/bin/activate
    Still broken? Use the full path: ./.venv/bin/python -m pytest -q

"No module named app"
    You're in the wrong folder, or you need PYTHONPATH=. in front of the
    command. Run from backend/.

"ANTHROPIC_API_KEY is not set"
    The key lives in backend/.env, which is gitignored. Only the judged eval
    and the reflection step need it. Add --no-judge to skip it.

"Client.__init__() got an unexpected keyword argument 'app'"
    Every test in tests/test_api.py errors like this when httpx is too new.
    FastAPI 0.104 ships an old starlette whose TestClient uses a shortcut that
    httpx 0.28 removed. Fix: python -m pip install 'httpx==0.27.2'
    (it's pinned in requirements.txt for this reason).

Port already in use
    Something's still running from last time. Change the port, or:
    lsof -ti:8000 | xargs kill
